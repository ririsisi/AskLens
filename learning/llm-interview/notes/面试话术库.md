# 面试话术库

> 这里沉淀「和导师一起打磨过、可直接背诵」的面试话术。
> 每条包含：**触发问题** + **30 秒电梯版** +（可选）**2 分钟深挖版** + **扛追问要点**。
> 导师每次走完 `★话术` 步骤后，会把成稿追加到这里。指标如为"观测趋势"会标注，绝不编造精确数字。

## 模块 02 · 核心框架

### ReAct（推理-行动-观察）+ AskLens 落地

**触发问题**：
- "你这个智能助手是怎么用 Agent 做知识库问答的？"
- "为什么不直接把检索结果拼进 prompt 一次性生成？"

**30 秒电梯版**：
> 我的助手用的是 Spring AI Alibaba 的 ReactAgent，走 ReAct 的"推理-行动-观察"循环。和传统 RAG"每次都检索、拼进 prompt、一把生成"不同，我让模型**自己决定要不要查、查什么**——闲聊就不检索，要查才调知识库工具。关键是 **Observation（检索证据）由程序生成**，模型不能伪造，这样答案被锚定在真实证据上、压住幻觉。我还设了两道防护：图最多跑 10 步、以及单轮只允许检索一次的守卫，避免模型陷入无效的工具调用死循环。

**2 分钟深挖版（在 30 秒基础上展开）**：
- 证据回传时带**证据等级 / 证据不足信号**，模型在证据弱时可以主动拒答（→ 幻觉抑制，详见后续 RAG 模块）。
- 底层检索是 RRF 混合检索（向量 + ES），后面 RAG 模块展开。

**扛追问要点**：
- *Observation 为什么不能模型生成？* —— 一旦模型能伪造证据，"接地（grounding）"就崩了，等于把幻觉合法化。所以由执行器（`qaRetrievalService`）生成并校验。**（注意：是"程序/系统"生成，不是"人为"）**
- *两道防死循环闸门*：① `recursionLimit(10)`——图最多跑 10 步（一步=一次模型推理或一次工具执行），跑满强制收尾；② `hasCompletedSearch()` 守卫——单轮重复调工具时返回 `DUPLICATE_TOOL_CALL`，逼模型基于已有证据作答。
- *源码位置*：`assistant/agent/AssistantReactAgentFactory.java`（Agent 工厂、recursionLimit）、`AssistantKnowledgeBaseTool.java`（工具/Observation/重复守卫）。

### ReAct vs CoT vs Plan-and-Execute（三框架对比）

**触发问题**：
- "说说 ReAct 和 CoT、Plan-and-Execute 的区别。"
- "什么任务用 ReAct，什么任务用 Plan-and-Execute？"

**30 秒电梯版**：
> 三者都让模型把思考写出来，区别在**接地**和**规划时机**。CoT 是纯闭卷推理，没有外部反馈，错了只能自省、容易幻觉。ReAct 在思考之上加了**行动→真实观察**的闭环，用工具的真实结果边做边纠错，适合下一步依赖上一步结果的任务，比如排查日志、RAG 多轮检索。Plan-and-Execute 则是开局先出完整计划再执行，适合步骤清晰、能预知路线的任务，比如数据流水线、批量改代码。

**扛追问要点**：
- *CoT 的命门*：闭卷、无 Action/Observation，纠错只能靠模型自省 → 易幻觉。
- *ReAct 的核心*：关键不是"多了两步"，而是 Observation 是**真实工具结果**，靠它**接地 + 纠错**。
- *Plan-and-Execute 的主场判据*：步骤多、依赖关系清晰、**开局即可预知路线**；反之"下一步强依赖上一步真实结果、路径事先不确定"的任务该用 ReAct。
- *别举错例子*：查快递（单步、无动态依赖）不是好例子；排查线上故障（看日志才知下一步查 DB 还是查网络）才是 ReAct 典型。

### Reflexion（反思—重试框架）

**触发问题**：
- "讲讲 Reflexion 框架。"
- "Reflexion 和让模型自己检查一遍有什么不同？"

**30 秒电梯版**：
> Reflexion 补的是 ReAct 的一个短板——ReAct 的纠错只在单轮循环里，任务一结束教训就没了，下一轮还会犯同样的错。Reflexion 在一整轮做完之后加了三个角色：Actor 负责做、Evaluator 评判这轮成败、Reflector 把失败原因写成一条**具体可执行**的反思（比如"计算前先做单位换算"），存进记忆带到下一轮重试。本质就是给 Agent 配了本"错题本"，跨尝试积累教训。

**扛追问要点**：
- *核心循环*：**Act → Evaluate → Reflect → Retry**（重试，不是"重拾"）。
- *三角色*：Actor（做/可调工具）、Evaluator（评判对错/打分，来源可为测试用例、规则、更强模型）、Reflector（写反思文本）。
- *反思的标准*：必须**具体、可执行（actionable）**——定位具体错误原因 + 明确改进策略；空泛的"我要更仔细"无效。
- *vs 自检*：自检一次性、口号化；Reflexion 把反思**结构化 + 跨尝试复用**，形成可累积的策略记忆。
- *vs Re-planning*：Re-planning 改的是**计划结构**（下一步怎么走）；Reflexion 改的是**策略/经验**并跨轮复用。
- *适用*：可验证任务（代码/数学/有测试用例）、易犯系统性错误、预算允许多轮重试。

### LATS（语言 Agent 树搜索）

**触发问题**：
- "你了解 LATS 吗？讲讲它和 ReAct 的区别。"
- "Agent 走错一步、错误又暴露得很晚，怎么办？"

**30 秒电梯版**：
> ReAct 是单链、贪心、不可回溯的——一条路走到黑，第 2 步选错可能要到第 6、7 步才暴露，发现了也退不回去重选。LATS 把决策过程从一条链改成一棵**搜索树**：每个节点由 **LLM 当裁判打分**，优先探更有希望的分支；走到死胡同就把"坏结果"**回传**给祖先节点更新评分，下次选得更准，还能叠一层失败**反思**避免重蹈覆辙。本质是把 MCTS 搬到 Agent 上。代价是 **LLM 调用次数暴涨、又慢又贵**，所以它主要在论文/刷榜，生产几乎不用，包括我的 AskLens 还是用 ReAct。

**扛追问要点**：
- *ReAct 的命门*：单路径 / 贪心 / 不可回溯，错误暴露越晚浪费越多，且无法回岔路口换路。
- *LATS 四步（=MCTS）*：选择（按分数+UCT 平衡利用与探索）→ 扩展+评估（LLM 生候选并打分）→ 模拟（往下试几步看结果）→ **回传/反向传播**（把好坏分数沿树回给祖先，更新评分）。
- *LLM 的双重身份*：既是 Actor（生成动作），又是 **value function / Evaluator（给节点打分）**；失败时再当 Reflector 写反思（复用 Reflexion 思想）。
- *措辞别说错*：LATS 提高的是**任务成功率 / 答案正确率**，不是"调用成功率"。
- *为什么生产不用*：树搜索反复调 LLM，调用数是 ReAct 的数倍～数十倍，延迟高、成本高，工程 ROI 太低。
- *一句话定位*：**树搜索（可回溯+多分支）+ LLM 打分 + 失败反思**，拿成本换成功率。

### LangChain vs LangGraph + AskLens 图引擎落地

**触发问题**：
- "说说 LangChain 和 LangGraph 的区别。"
- "你说你的 Agent 用了图引擎，为什么需要图、用链不行？"

**30 秒电梯版**：
> 链是单向的，撑不起 ReAct"思考→行动→观察→再思考"这种带**循环**的模式。图有节点、条件边和贯穿全程的共享状态，天然适配。我的 AskLens 助手就建在 Spring AI Alibaba 的图引擎上：KB_SEARCH 模式下我把知识库检索作为**工具注入**进图，图里"模型推理节点"和"工具执行节点"靠**条件边**循环——模型每轮自己决定要不要再查一次，**直到它不再调用工具、基于已有证据给出最终答案**；我还设了 `recursionLimit(10)` 给这个循环兜底，防止图无限绕下去。

**扛追问要点**：
- *根本矛盾*：LangChain 是 Chain（DAG/单向，一进一出），表达不了"环 + 按条件分叉"；ReAct 的循环要"绕回去"，形状对不上 → 需要图。
- *LangGraph 三件套*：节点（Node，一个处理步骤）+ 条件边（Conditional Edge，按结果决定下一跳，实现分支/循环）+ 状态（State，贯穿全程的共享对象，是跨步骤记忆的载体）。
- *别混淆 ReAct vs LATS*：ReAct 的循环是"思考→行动→观察"**不回退**；**"回退/回溯"是 LATS（树）的能力**。讲图时说"循环"，别说"回退"。
- *别混淆 注入 vs 调用*：工具是**创建 Agent 时一次性注入**（`builder.methodTools`）；循环里反复发生的是模型**决定要不要再调用**。终止条件 = 模型不再调用工具。
- *源码挂点*：包名 `com.alibaba.cloud.ai.graph`（全是 graph）；`CompileConfig.recursionLimit(10)`（图的循环上限，链没这概念）；`MemorySaver`（图运行态 checkpoint / 状态持久化）；`AssistantReactAgentFactory.java`。

## 模块 03 · RAG 检索与问答（V3）

### 查询规划（DIRECT / REWRITE / DECOMPOSE）

**触发问题**：
- "你的 RAG 系统拿到用户问题后，第一步做了什么？为什么要做？"
- "为什么不直接拿用户问题去查向量库？"

**30 秒电梯版**：
> 拿到问题后我**不会**直接拿原话去检索——那是 demo 做法。第一步是**查询规划**：用一次轻量 LLM 调用把问题分三类。像"它和上一版比怎样"这种**指代不清**的，改写成自包含查询（REWRITE）；一句话里塞了多个问题的，拆成子查询分别检索（DECOMPOSE）；本来就清晰的直接查（DIRECT）。这么做是因为**用户原话往往不适合直接检索**——指代、口语、复合问题都会拉低召回。而且这步是"锦上添花"，所以规划一旦失败就**静默降级回原问题直查**，绝不阻断主流程。

**扛追问要点**：
- *三策略治什么病*：REWRITE 治"指代/上下文模糊"（"它""上一版"语义向量飘）；DECOMPOSE 治"一句多问"（多主题稀释向量相关性）；DIRECT 省 token。
- *为什么降级到 DIRECT 而不是 REWRITE*：降级发生时那次规划 LLM 调用**本身失败了**，手上**只有原始问题**，没有改写后的查询——REWRITE 无输入可用。DIRECT 是唯一"保证可用"的安全垫（do no harm）。
- *没有重试*：`plan()` 是单次 try，catch 任何 `RuntimeException` 直接 `QueryPlanResult.fallback()`→DIRECT；`validatePlan` 里 strategy 为 null / queries 为空也全走 fallback。
- *子查询上限*：`MAX_QUERY_COUNT = 3`，`limitQueries` 硬截断。
- *源码位置*：`qa/service/QueryPlanningService.java`、`qa/model/QueryPlanResult.java`、`QueryPlanStrategy.java`。

### RRF 混合检索融合（为什么不直接加分 + k=0 的讲究）

**触发问题**：
- "向量 + 关键词两路结果，你是怎么融合的？为什么不把分数直接加起来？"
- "RRF 的 k 业界一般取 60，你为什么取 0？"

**30 秒电梯版**：
> 两路分数不能直接相加——向量是 0~1，BM25 能到几十，直接加等于让 BM25 一家独大，向量语义那路就成了噪声，混合检索白做了。所以我用 **RRF**：不看原始分，只看**排名**——一个切片在每一路里排第几名，按 `1/(k+rank)` 取倒数再求和，两路都靠前的自然冒头。排名是 scale 无关的，天然可比。一个细节是 k 我取 **0** 而不是默认的 60——因为这个融合分在我系统里**不只排序，还要当可信度**驱动证据分级和拒答；k=60 会把分数全压平、够不到我设的 0.85 阈值，k=0 才能拉开区分度。

**2 分钟深挖版（在 30 秒基础上展开）**：
- *为什么加权求和不行*：两路值域不可比，加权融合天然偏向数量级大的一路；极端例子——切片 A（BM25 40 + 向量 0.6 = 40.6）会碾压语义近乎完美的切片 B（向量 0.95 + BM25 5 = 5.95），融合退化成纯关键词检索。
- *RRF 公式*：`Σ 1/(k+rank_i(d))`，对每个通道取倒数排名再求和。倒数让"越靠前分越高、头部差距大尾部差距小"；求和实现"多路 / 多查询都命中的切片累加冒头"。
- *k=0 的数字证据*：k=60 时 rank1=1/61≈0.0164、rank2=1/62≈0.0161，几乎无差；k=0 时 rank1=1.0、rank2=0.5，差 0.5。k=0 极大拉开头部区分度。
- *分数复用*：原始 RRF 分经 `1-e^(-x)` 归一化到 0~1；单通道 rank-1（原始分 1.0）→0.63，双通道 rank-1（原始分 2.0）→0.86 > 0.85 → 判定 SUFFICIENT。**阈值是按 k=0 标定的**，两者配套。

**扛追问要点**：
- *RRF 凭什么更鲁棒*：只用排名、不用原始分 → scale 无关，不会被某一路的数量级绑架。
- *多查询/双通道分数累加*：候选放进同一个 `LinkedHashMap`，每次命中累加 `rankingScore`；检索**串行**执行（for 循环 + 上限 3），规避并发写共享 map 的结构层 + 累加层竞态，且收益小（耗时大头在最后 LLM 生成）。
- *k=0 的小代价*：越小越敏感于头部排名抖动，但下游有证据分级 + 邻居窗口兜底，可接受。
- *源码位置*：`qa/rag/HybridChunkRetrievalService.java`（`RRF_K=0`、`reciprocalRank`、`normalizeScore`、`evaluateEvidenceLevel`）。

### 邻居窗口扩展（为什么 ±1）

**触发问题**：
- "检索命中的切片，你是直接喂给模型吗？"
- "邻居窗口为什么是 ±1，不是 ±2、±3？"

**30 秒电梯版**：
> 切片是机械按 token 切的（约 240 token 一片），一个完整意思可能正好被边界拦腰切断。所以命中某切片后，我会把它前后各一个切片拼进去（±1）恢复上下文，避免模型拿到半句话误解。窗口不开更大，是成本权衡：窗口越大，喂给 LLM 的 token 越多、成本越高，还会拼进大量不相关切片当噪声、稀释真正的信号。而且 V2 切片时已经留了 32 token 的 overlap 做边界缓冲，所以 ±1 基本够覆盖绝大多数被切断的语义，是"完整性 / 成本 / 噪声"的甜点位。

**扛追问要点**：
- *顺序别记反*：RRF 融合排序 → 取 Top-K → 类簇聚合 → 邻居窗口扩展。先用分数筛选，再对幸存者做昂贵的回库窗口扩展（不会对上百候选全做）。
- *overlap vs 邻居窗口*：overlap 是切片阶段的"预防"（相邻切片共享 32 token）；邻居窗口是检索阶段的"补救"（运行时回库取相邻切片拼接）。两者叠加。
- *源码位置*：`HybridChunkRetrievalService.java`（`DEFAULT_NEIGHBOR_WINDOW=1`、`buildEvidenceWindow`、`expandedStart/EndChunkIndex`）。
